Does In-Loop LLM Review Make Patches Correct, or Only Make Them Pass? A Research Gap in Repository-Level LLM4APR

Research Gap Statement · Lab 5, Research Methods (Week 5) · Rifqi Wibisono (魏副棋), L25020014 · Bottleneck selected: patch correctness (with cost), from the MAGIS paper [2] and the LLM4APR review [1]

1. Background and state of the art

LLM-based automated program repair (LLM4APR) grew from one study in 2020 to 189 by September 2025, and its frontier has moved from single-function bugs to repository-level issue resolution [1]. The standard testbed, SWE-bench, gives a model a real GitHub issue and a full Python repository. It counts the issue as resolved when the model's patch makes the developer's hidden tests pass [3]. Directly prompted models resolve almost nothing in this setting: GPT-4 resolves 1.74% even when given the files to edit. The field responded with agentic pipelines. MAGIS [2] divides the work among four LLM roles: Manager, Repository Custodian, Developer, and a Quality Assurance (QA) Engineer that reviews every code change and returns it for revision until it approves. MAGIS reports 13.94% resolution. In-loop review has since spread to other systems [9].

2. The specific unresolved gap

All these gains are measured by one oracle: the tests that shipped with the developer's fix. Tests are an incomplete specification, and APR research has known since Qi et al. [7] that test-passing (plausible) patches are often wrong: GenProg's 55 reported fixes contained 2 correct ones. The problem persists at repository scale. On SWE-bench Verified, the human-filtered 500-issue subset, the full test suite fails 7.8% of patches counted as resolved. Differential testing shows 29.6% behave differently from the developer's patch, and an estimated 11% of plausible patches are incorrect, inflating reported resolution by 6.4 points [4]. Test augmentation exposed 345 mislabelled patches [5] and cut top agents' resolved rates by 4.2–9.0% [6].

Against this, MAGIS credits its QA reviewer with +3.31 points with issue hints and +1.57 without [2]. These gains are smaller than the measured inflation and are measured by the same oracle that produces it.

Gap: whether in-loop LLM review makes patches more correct, or mostly turns failing patches into plausible-but-incorrect ones, has not been measured. None of the six LLM-based patch-correctness assessors in the LLM4APR review was evaluated on repository-level issue patches [1, §8.3].

3. Why existing approaches fail (root cause)

The reviewer sees text, not behaviour. MAGIS's QA Engineer is the same model reading a diff, so it inherits the generator's blind spots. Olausson et al. found self-repair is bottlenecked by exactly this: a model's ability to diagnose its own code [8].

The errors that survive testing are largely invisible in a diff. 27.3% of behaviourally divergent patches change more behaviour than the developer's fix, and faulty supplementary changes cause 36.4% of the patches confirmed incorrect [4]. A side effect on an untested path neither appears in the diff nor is exercised by an issue-specific test.

Execution-aware review checks the intended change, not unintended ones. SpecRover's reviewer and Agentless's validation run reproduction and regression tests [9, 11]. These confirm the reported symptom is gone and already-tested behaviour is preserved, but say nothing about untested behaviour the patch altered.

Review has no correctness feedback signal. Reviewers are designed and scored against the same weak tests, so pushing a patch to pass rather than to be right is rewarded. The 2026 review-loop preprints (SWE-Review, RETRACE) also report gains on the original tests only.

Cost is unreported. MAGIS gives no token or monetary cost, so whether review pays for itself is unknown, an omission Kapoor et al. identify as distorting agent research [12].

4. Proposed intervention and expected contribution

Intervention: differential review. Before the reviewer decides, the pipeline generates and executes inputs on which the original and the patched repository behave differently. The reviewer must justify each observed difference against the issue text, or reject the patch and return the differentiating input as concrete feedback. This brings DiffTGen's idea of exposing original-versus-patched differences [10] into the LLM review loop. It reuses PatchDiff's call-trace-guided test generator [4], with one change: PatchDiff compares against the developer's patch, which exists only at evaluation time, while differential review compares against the original program, which is available at repair time.

Evaluation. We will run inside MAGIS's released implementation, whose QA step is a configuration switch and which records the pre-review patch. The benchmark is SWE-bench Verified, with one fixed low-cost model, the files to edit supplied (holding localisation constant) and issue hints disabled (they can leak solutions). Each instance yields paired patches under no review, text-only review and differential review. Each patch is scored by the original tests and by a strengthened oracle: the full developer test suite, PatchDiff against the developer's patch, augmented tests where released [5, 6], and two-rater manual adjudication of divergent patches.

Expected contributions: (1) the first measurement of how much of in-loop review's gain survives a strengthened oracle; (2) a review mechanism aimed at the failure class tests miss; (3) the cost per correctly resolved issue of each review design. The novelty claim is deliberately narrow: review and differential testing each exist; what is new is their controlled combination, evaluated beyond the benchmark's own tests.
